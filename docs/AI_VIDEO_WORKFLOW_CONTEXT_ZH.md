# pdoom-video 制作方式与复用上下文

> 用途：作为新对话窗口的补充上下文，说明这个项目如何生成视频、Skill 在其中扮演什么角色，以及如何把同样的方法复用于游戏宣传片。

## 一句话结论

`pdoom-video` 本质上是一个**代码渲染的音乐视频项目**：音频分析工具先把完整歌曲拆成歌词时间、节拍、段落、响度等结构化数据，AI 编程模型再根据这些数据设计分镜并编写 TypeScript/Three.js 画面，浏览器逐帧渲染，最后由 FFmpeg 合成音频和视频。

它不依赖视频生成模型。画面主要来自 HTML Canvas、Three.js、WebGL/GLSL、字体、程序化图形和少量代码生成的静态素材。

## 1. 原项目是否使用了 Skill

公开仓库中没有 `SKILL.md`，也没有证据表明原作者使用了 Codex/Claude Skill。原项目 README 说明，它由 Claude Opus 5.5 在 Claude Code 中通过持续对话完成，包括：

- 概念与视觉方案；
- 歌词对齐和音频分析；
- 渲染器；
- 每个场景的代码；
- 最终渲染。

因此应区分：

- **原始 pdoom-video**：Claude Opus 5.5 + 编程工具 + 音频分析工具；
- **其他作者用 GPT-6 Luna 演示或复现**：可能另外使用了私有或本地 Skill，但这不是原仓库的必要依赖。

Skill 不是模型，也不是渲染器。Skill 更像一份可复用的制作 SOP，告诉 Agent 应该依次做什么、调用哪些工具、怎样验收结果。例如：

1. 读取宣传需求和素材；
2. 分析完整音频；
3. 生成分镜和时间线；
4. 编写或修改场景代码；
5. 小范围预览；
6. 修正节奏和视觉问题；
7. 调用浏览器和 FFmpeg 完成最终渲染。

## 2. GPT-6 Luna 是否直接理解完整音频

要分成模型层和工作流层：

- **模型层：不是。** GPT-6 Luna 当前不原生接收音频或视频输入。
- **工作流层：完整音频会被处理。** Agent 调用外部音频工具分析整首 MP3，再读取工具产生的结构化结果。

该项目的音频处理大致如下：

```text
完整 MP3
  ↓
Demucs 等工具分离人声、鼓和伴奏
  ↓
Whisper + CTC 对齐歌词和单词时间
  ↓
检测 BPM、beat、downbeat、onset、段落和响度
  ↓
data/lyrics.json + data/audio.json
  ↓
AI 模型根据这些数据设计画面和剪辑时间线
```

所以“GPT 听懂了音乐”是一种工作流层面的简称。更准确的说法是：

> 音频模型和信号处理工具负责听、识别和测量；GPT/Claude 负责理解结果、导演画面并修改代码。

## 3. 项目中的视频渲染方式

核心路径是：

```text
TypeScript / Three.js / Canvas / WebGL
  ↓
Chrome 或 Chromium 按指定时间渲染每一帧
  ↓
原始 RGBA 帧通过管道交给 FFmpeg
  ↓
FFmpeg 使用 H.264 等编码器压缩视频并混入原始音频
  ↓
最终 MP4
```

这里提到的“ffm”大概率就是 FFmpeg，或者是对 FFmpeg 的非正式简称。FFmpeg 不负责创作画面，它负责编码、混音、拼接和输出最终视频。

## 4. 音乐来源与自行生成音乐

原项目使用的歌曲版本由 Suno 生成，更早的版本使用过 Udio。歌曲、歌词和仓库中的音乐文件并不随代码的 MIT 许可证一起授权，商用时必须单独确认音乐权利。

可以考虑以下方案：

### Suno：商业服务，最省事

适合快速生成包含人声、歌词和伴奏的完整歌曲，也可以生成纯音乐。制作游戏宣传片时，应明确时长、风格、前奏、高潮位置和结尾 Logo 定格空间。

如果需要商业使用，应在符合其商业授权的付费方案下生成，并保存生成时间、账户方案和授权条款记录。可商业使用不一定等同于作品在所有司法辖区都能获得完整版权保护。

### ACE-Step 1.5：开源、本地化首选

适合希望本地部署、批量生成、接入 Agent 或进一步控制 BPM、调性、时长、参考音频和局部编辑的场景。相较 Suno，需要承担模型部署、GPU、参数调试和质量筛选成本。

简单选择：

- 先验证宣传片创意：Suno；
- 建设长期自动化产品：ACE-Step 1.5；
- 宣传片不需要唱词时，优先生成纯音乐，能显著降低歌词对齐和画面语义设计难度。

## 5. 新游戏宣传片是否每次都要重写 TypeScript

需要重新创作一部分，但不需要重写整个系统。

### 可长期复用

- 音频分析脚本；
- 浏览器逐帧渲染器；
- FFmpeg 编码与混音流程；
- 时间线和节拍吸附逻辑；
- 横版、竖版和分辨率配置；
- 字幕、Logo、HUD、粒子、闪白、镜头抖动、转场、CTA 等通用组件；
- 预览、分段渲染和最终质量检查脚本。

### 每个游戏需要重新制作

- 宣传角度和目标观众；
- 分镜和叙事结构；
- 游戏录像的选段；
- 音乐与画面的对应关系；
- Logo、卖点文案和商店 CTA；
- 专属视觉风格；
- 部分新场景组件、TS 场景代码以及时间线配置。

理想架构不是让模型每次重写全部 TS，而是建立：

```text
稳定渲染引擎
  + 可复用场景组件库
  + 每条宣传片的 timeline/config
  + 少量项目专属场景代码
```

如果只是替换文案、素材或颜色，可能只需要修改配置；如果视觉概念完全不同，才需要增加新的 TS 场景组件。

## 6. 推荐的游戏宣传片制作流程

不要一开始就精确卡音乐。比较稳妥的顺序是：

1. 输入游戏录像、Logo、名称、商店描述和目标平台；
2. AI 找出 3～5 个最值得宣传的玩法或视觉瞬间；
3. 先做粗分镜，确定开头钩子、玩法展示、高潮和 CTA；
4. 根据粗分镜选择或生成音乐；
5. 锁定最终音频，不再随意替换；
6. 对完整音频做节拍、段落、歌词和响度分析；
7. AI 生成精确时间线，复用组件并编写少量专属 TS；
8. 先渲染关键帧和短区间，检查节奏、字幕和画面；
9. 修正后完成整片渲染；
10. 输出横版、竖版、静音字幕版等渠道变体。

如果更换音乐，通常必须重新分析音乐、调整时间线并重新渲染；但渲染引擎和通用组件不需要重做。

## 7. 对游戏宣传片的推荐形式

建议采用混合模式，而不是完全用代码重新绘制游戏：

- 真实游戏录像：准确展示玩法和美术；
- HTML/Canvas/Three.js：制作字幕、HUD、数据、Logo、转场和程序化特效；
- FFmpeg：剪辑、混音、字幕烧录、尺寸转换和编码；
- 可选的视频生成模型：仅用于游戏里不存在的概念镜头、电影化过场或氛围补充镜头。

这能避免视频生成模型篡改角色、UI 和玩法，同时保留强烈的视觉包装。

## 8. 新窗口可以直接使用的任务描述

可将下面内容直接交给新的 AI 窗口：

```text
请先阅读本文件、项目 README、docs/TREATMENT.md、docs/ENGINE.md，理解 pdoom-video 的代码渲染与音频驱动架构。

目标不是调用视频生成模型直接生成整片，而是：
1. 使用音频分析工具处理完整音乐；
2. 将歌词、节拍、段落、响度等结果保存为结构化数据；
3. 使用 TypeScript、Three.js、Canvas 或 WebGL 制作确定性画面；
4. 让场景时间线对齐音乐关键点；
5. 用 Chromium 逐帧渲染；
6. 用 FFmpeg 合成最终视频。

请优先复用现有引擎、渲染脚本和通用组件，只为新宣传片新增时间线配置和必要的专属场景。修改前先说明计划，并用关键帧或短区间进行视觉验证。
```

## 9. 最终判断

- 该项目不是 HTML 页面录屏，而是浏览器作为图形渲染器，离线、确定性地逐帧输出。
- 它不要求视频生成模型。
- 完整音频由外部工具分析，LLM 读取分析结果，不是 Luna 原生听音频。
- Skill 可以把整套制作步骤标准化，但不是生成能力本身。
- 新宣传片需要新的创意、时间线和部分场景代码，但大部分底层工程应当复用。
- 最适合游戏宣传片的方案是“真实游戏录像 + 程序化包装 + 音乐驱动时间线”。
